# `test/tutorials/` —— 教程复现程序（骨架）

## 1. 用途

存放「**教程/流程图 → 场景文件**」的复现程序：把一篇真实老教程读懂之后，
用 L2 固定程序把它重建出来，并逐帧导出成场景文件（#96 §6.1 / §7）。

**本单（#103）只建骨架与门槛**——首个真实样本（灰机 Wiki「太阳能级硅（多晶硅）」，
裁决 8）的程序入本目录是 **#106 F2 的交付物**。这样切分的理由：多帧导出依赖 `record`/`export`
的 cp 入口（#102），#103 时它尚未落地，硬写一份跑不通的程序只会变成一份「看起来像资产」的死文件。

## 2. 命名规范

- 一个教程一个目录，目录名 = 教程 slug（**kebab-case**）；
- 每个教程目录固定三件：
  ```
  tutorials/<slug>/
    program.json    # L2 固定程序（lightning.case/1，用 action 段编排 L0/L1）
    SOURCE.md       # 教程出处（URL + 取用日期）+「读懂 → 重建」映射表
    frames.md       # 逐帧导出脚本（每帧的世界状态 + record/export 顺序）
  ```
- 允许**两级**（教程目录 / 三件文件），不再加深。

## 3. 入库门槛检查单（逐条可判定）

- [ ] **① 固定请求序列**：`program.json` 自包含；`frames.md` 里**逐帧**给出世界状态与
      `record`/`export` 顺序（多帧 = 同会话多次录制后合并，#96 §6.1）
- [ ] **② 固定世界重建参数**：`world` 段 `void:true` + 固定 `seed`/`base`；**逐帧前置逐条写死**；
      **同会话纪律**：多帧必须落在同一会话同一导出缓冲，跨会话拼接**不算**合法产物
- [ ] **③ 期望产物**：场景文件（`format_version:"2.0"` + `frames[]`）+ **关键帧的读面记录**
      （证明该帧世界状态确实是想要的那个）+ `SOURCE.md` 的教程出处
- [ ] `SOURCE.md` 写明**教程原文出处**（URL）与**取用日期**（教程会变，基准要能追溯）
- [ ] **如实记录失败与重试**（#106 F2：教程复现程序的定位是**能力体检**，失败流水是交付物的一部分）
- [ ] **L0/L1 分层标注**：布景走 L0（供电、输入物料），**机器操作与验证必须走 L1/读面**
      （L0 的产物不能当 L1 的证据，#96 §4.2）
- [ ] 场景文件被既有消费方（工作台/Wiki 链路）解析通过
- [ ] 命名 kebab-case；本目录与 `test/README.md §1.3` 的索引行已补

## 6. 为什么门槛先于样本

「可重放」这条硬要求（#96 §7）在教程场景里最容易失守：教程原文会变、多帧必须同会话、
L0 布景很容易被当成 L1 的证据。把门槛先写成可判定的检查单（本文件 §3），
样本交付时才是**被门槛约束的**，而不是「先跑起来再说、门槛以后再补」——
后者在本仓已有先例（老设施的触发文件约定从没被写成门槛，于是没人知道它到底要求什么）。
